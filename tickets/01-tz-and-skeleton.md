Коллеги, у нас новый заказчик — управляющая компания «Северный квартал». Сергей Петрович прислал письмо: [letters/01-goncharenko.md](../letters/01-goncharenko.md). Прочитайте его целиком, прежде чем что-то писать.

Кода по письму заказчика мы пока не пишем. Сначала — ТЗ: что именно делаем, как поймём, что сделали, и что спросить у заказчика, пока не поздно. Письмо написано живым языком, и в нём есть места, которые противоречат друг другу. Найти их сейчас стоит час, а после сдачи — месяц переделок.

## Что сделать

### 1. Черновик ТЗ — `docs/TZ.md`

Заготовка уже лежит в репозитории, структура — по ГОСТ 34.602-2020, сокращённая для черновика. Заполните все разделы:

- **4.1** — не меньше восьми функциональных требований: `- ФТ-01. Текст. [А2]`. Одно требование — одно проверяемое действие программы или пользователя. «Программа должна быть удобной» — не требование.
- **4.2** — не меньше четырёх нефункциональных требований, **каждое с числом**: время, объём, количество. «Поиск быстрый» — не требование; «заявка находится по номеру телефона не дольше чем за 1 с при 150 000 заявок в базе» — требование. Числа, которых нет в письме, — ваше предложение заказчику, отметьте это.
- После каждого требования — абзацы письма, из которых оно следует: `[А5]` или `[А3, А6]`. Каждый абзац с требованиями (А2–А10) должен быть покрыт хотя бы одним требованием.
- **5** — не меньше пяти вопросов заказчику, каждый со ссылкой на абзац и знаком «?». Лучшие вопросы — те, без ответа на которые нельзя начать проектирование. Подсказка: сравните [А2] и [А10] — кто на самом деле отмечает выполнение? А [А1] и [А3] — сколько аварийных заявок в час ночью может обработать один диспетчер?

На второй паре обсудим черновики вместе: какие противоречия нашли, какие числа предложили.

### 2. Каркас проекта — `CMakeLists.txt` и `src/main.cpp`

`CMakeLists.txt` в корне пишете вы. Требования:

- `project(dispatch VERSION 0.1.0 LANGUAGES CXX)` — версия программы записана **только здесь**;
- сразу после `project()` — `include(cmake/flags.cmake)`: C++20, предупреждения как ошибки, санитайзеры;
- программа `dispatch` из `src/main.cpp`.

Версию в код передаёт CMake: файл-шаблон `src/version.hpp.in` с `@PROJECT_VERSION@` превращается при настройке сборки в настоящий заголовок.

```cmake
configure_file(src/version.hpp.in ${CMAKE_CURRENT_BINARY_DIR}/generated/version.hpp @ONLY)
add_executable(dispatch src/main.cpp)
target_include_directories(dispatch PRIVATE ${CMAKE_CURRENT_BINARY_DIR}/generated)
```

```cpp
// src/version.hpp.in
#pragma once
namespace dispatch {
inline constexpr const char* kVersion = "@PROJECT_VERSION@";
}
```

Поведение программы:

| Запуск | Вывод | Код возврата |
|---|---|---|
| `dispatch --version` | `dispatch 0.1.0` | 0 |
| `dispatch --help` или без аргументов | справка: первая строка `Использование: dispatch <команда> [параметры]`, дальше строки про `--version` и `--help` | 0 |
| `dispatch --bogus` (любой неизвестный параметр) | в **stderr**: `неизвестный параметр: --bogus` и подсказка про `--help` | 2 |

Аргументы командной строки — параметры `main`: `int main(int argc, char* argv[])`, `argv[0]` — имя программы. Сравнивать удобно через `std::string_view arg = argv[1]; if (arg == "--version") …`.

Строка `0.1.0` не должна встречаться в `src/` нигде, кроме `version.hpp.in`, — проверка это ищет.

## Критерии готовности

- `make check-tz1` и `make check-cli1` зелёные.
- `./build/dispatch --version` печатает `dispatch 0.1.0`; после смены версии в `CMakeLists.txt` и пересборки — новую, без правки кода.
- Работа — в ветке `dsp-1` и pull request в `main`. В описании PR — три главных противоречия в письме, которые вы нашли, и как предлагаете их решить.
