# DSP-13. Стандарт кода, документация и импорт старых заявок

**Автор:** Марина Кольцова, тимлид · **Неделя:** 13

До сдачи две недели. Код «Диспетчера» будут сопровождать другие люди — значит, он должен читаться одинаково и быть описан. Заказчик по ТЗ получает описание программы [раздел 7 ТЗ]. И Сергей Петрович прислал выгрузку старой программы [В1–В7]: прошлогодние заявки должны попасть в «Диспетчер» [А9, Б6]. Разовая перекладка данных — работа для скрипта, и писать его удобнее на Python.

## Что сделать

### 1. Стандарт кода

В корне проекта лежат `.clang-format` и `.clang-tidy` курса (если их нет — `make update` положит).

- Весь ваш код — `src/`, `include/`, `tests/` — оформлен: `clang-format --dry-run --Werror` молчит. Проще всего — `clang-format -i` по всем файлам и «форматировать при сохранении» в среде.
- Проверка — clang-format 18.1.3, как в GitHub Actions: `pipx install clang-format==18.1.3`, если ваша версия спорит с проверкой.
- clang-tidy по `.clang-tidy` не находит ничего в `src/core/*.cpp` и `src/cli/*.cpp`. Подавлять замечание `// NOLINT(…)` можно только с объяснением в том же комментарии.

### 2. Документация интерфейса

Всё публичное в `include/dispatch/*.hpp` — с комментариями Doxygen: у файла `\file`, у классов, структур, их открытых полей и методов, у свободных функций — `\brief`, у параметров — `\param`, у результата — `\return`, у исключений — `\throws`. Проверка — `doxygen checks/doc13/Doxyfile` без единого предупреждения.

### 3. Описание программы — `docs/DESCRIPTION.md`

По ГОСТ 19.402-78, разделы:

1. `## 1. Общие сведения` — наименование, язык, что нужно для работы;
2. `## 2. Функциональное назначение` — какие задачи решает, ограничения;
3. `## 3. Описание логической структуры` — модули (`dispatch_core`, `dispatch`, `dispatch_gui_lib`, `dispatch-gui`), основные классы и как они связаны; главный алгоритм — хотя бы одной схемой (текстом или Mermaid);
4. `## 4. Используемые технические средства`;
5. `## 5. Вызов и загрузка`;
6. `## 6. Входные данные` — файл заявок, файл мастеров, выгрузка старой программы;
7. `## 7. Выходные данные`.

### 4. Импорт на Python — `tools/import_legacy.py`

```text
$ python3 tools/import_legacy.py старые.csv requests.csv
строка 7: дата: не дата «31.02.2025 10:00»
…
перенесено заявок: 34, пропущено строк: 6
```

- Только стандартная библиотека Python: `csv`, `re`, `datetime`. Старый формат и правила перевода — письмо 3.
- Результат — файл «Диспетчера» ровно в том виде, в каком его сохраняет `Registry::save`: BOM, заголовок, строки с `\r\n`, номера заявок по порядку с 1, подъезд — 1, срочность — `обычная`, выполненные — `закрыта` с исполнителем и датой выполнения в виде `ГГГГ-ММ-ДД ЧЧ:ММ`.
- Строки, которые не разобрать, — в stderr `строка N: причина` (N — номер строки старого файла, заголовок — 1), в результат не попадают; итог — последней строкой в stdout; код 1, если такие строки были, иначе 0. Пустые строки пропускаются молча. Файл не открылся, не Windows-1251 или не тот заголовок — сообщение и код 2.
- Причины — как в примере: `дата: не дата «…»`, `адрес: не разобрать «…»`, `телефон: не номер «…»`, `выполнено раньше создания`, `отметка: непонятно «…»`, `полей 4, нужно 6`. Выполнено, но исполнитель пуст — `выполнено, но нет исполнителя`; пустой текст — `текст заявки: пусто или перевод строки`.
- Результат проходит `dispatch check` без ошибок — это и есть связка Python и C++: скрипт готовит данные, программа их проверяет и работает с ними.
